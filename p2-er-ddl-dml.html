หน้าแรก • PART II — Smart Bus Bell & IoT Tracking System (อ.ผึ้ง)

🚏 E/R Chen → สร้างตาราง 11 ตาราง + ข้อมูล Seed — โค้ด DDL/DML เต็มพร้อมอธิบายทีละบล็อก

11 ตาราง + 7 SequenceWeak Entity · Junction · Derivedไฟล์ 1 → 2 (Oracle 10g R2)

① อาจารย์ต้องการอะไร (โจทย์ข้อนี้)

"1- DDL , DML ตาม E/R Diagram" + "ให้ DROP ทุกตารางแล้วสร้างใหม่ให้ดู Face-to-face" — สภาพจริงตอนนี้: สคริปต์ deploy บน server แล้วทั้งหมด (Oracle 10g R2 ผ่าน iSQL*Plus) — วันสอบแค่ รับซ้ำตามลำดับไฟล์ 1→5: ไฟล์ 1 (DDL) จะลบของเดิม เฉพาะที่ชื่อตรงกับโปรเจกต์นี้ แล้วสร้างใหม่ให้อาจารย์ดูทั้ง 11 ตาราง + 7 Sequence ต่อด้วยไฟล์ 2 (DML ใส่ข้อมูลทดสอบ 27 แถว)

🌱 มือใหม่อ่านก่อน (สำหรับคนที่ยังไม่เคยเขียน SQL)

  • โครงโค้ดทั้งหมดในหน้านี้ เหมือน Part I ทุกบรรทัด — เปลี่ยนแค่ "ชื่อตาราง/คอลัมน์/ธุรกิจ" ดังนั้นถ้าอ่านหน้า DDL/DML ของ Part I เป็นแล้ว หน้านี้อ่านผ่านเร็วมาก
  • ยังไม่ได้อ่าน? กลับไปดูหัวข้อ "อ่าน CREATE TABLE ทีละบรรทัด" และ "SELECT แรกในชีวิต + อ่าน INSERT" ก่อน แล้วกลับมา — ใช้เวลา 10 นาที คุ้มทั้งเทอม
  • สั้น ๆ อีกรอบ: CREATE TABLE = สร้างโครง · INSERT INTO ... VALUES ... = ใส่ข้อมูล 1 แถว · SELECT ... FROM ... WHERE ... = ดึงข้อมูลออกมาดู · COMMIT = บันทึกถาวร

Chen Model: สี่เหลี่ยม = Entity · กรอบซ้อน (กล่อง IOT) = Weak Entity · ข้าวหลามตัด = Relationship · วงรี = Attribute · เส้นประ = Derived Attribute ("จำนวนคนบนรถ" ไม่เก็บคอลัมน์ ต้องคำนวณ)

🧠 กฎแปลง E/R → ตาราง 3 ข้อ (โดนถามแน่ — ตอบสั้นได้ตรงนี้)

  • ความสัมพันธ์ N:M → ตารางกลาง (Junction Table) — เช่น "การกดกริ่ง ส่งสัญญาณ รถ" (N:M) กลายเป็น VEHICLE_BELL_REQUEST โดย PK = คู่ FK ทั้งสอง
  • Weak Entity → composite PK — "กล่อง IoT" ผูกกับรถแบบ Identifying Relationship → IOT_BOX มี PK = (VEHICLE_ID, BOX_ID) = PK เจ้าของ + Partial Key
  • Derived Attribute → ไม่เก็บคอลัมน์ — "จำนวนคนบนรถ" คำนวณจากแหล่งอื่น (ตัวนับ IoT/แอปคนขับ) จึงไม่มีคอลัมน์ใน VEHICLE
  • ทำไม ER ฉบับนี้ตัด APP กับ LOG ออก? — LOG ชนกับตาราง LOG ของงานอื่นที่มีอยู่แล้วบน server และ APP ไม่ได้ใช้จริง — USER จึงย้ายมาเป็นฝ่ายกดกริ่งเอง (ความสัมพันธ์ 1:N)

🧹 ขั้นที่ 0 — DROP ของเดิม "เฉพาะชื่อของโปรเจกต์นี้" (ไฟล์ 1 · ส่วนเปิด)

⚠️ ความต่างจากเว็บเก่า — Database User ตัวนี้มี "ของงานอื่น" อยู่ด้วย

  • Account นี้บน server มีตารางของงานอื่นอยู่รวมกัน: ADMIN, DEPARTMENT, DEPARTMENT_HEAD, DOCUMENT, DOCUMENT_DETAIL, EMPLOYEE, LOG, RECEIPT_RECORD — ห้ามลบ!
  • สคริปต์จึง ไม่ DROP ทิ้งทั้ง schema แต่ลบเฉพาะชื่อที่ตรงกับโปรเจกต์นี้ด้วย WHERE TABLE_NAME IN (...) — ปลอดภัยต่องานอื่น และ รันซ้ำได้ (idempotent: ไม่เจอก็ข้าม ไม่ error)
oracle_1_ddl.sql · ส่วน [0] ลบของเดิม 
-- ---------- [0.1] ลบ TABLE ของโปรเจกต์นี้ (ถ้ามี) ----------
BEGIN
  FOR r IN (SELECT TABLE_NAME FROM USER_TABLES
            WHERE TABLE_NAME IN (
              'VEHICLE_BELL_BUTTON','BELL_BUTTON','IOT_BOX','ALERT_STATISTICS',
              'VEHICLE_DIGITAL_SIGNAL','VEHICLE_BELL_REQUEST','DIGITAL_BELL_SIGNAL',
              'BELL_REQUEST','VEHICLE','USERS','USER_TYPE')) LOOP
    EXECUTE IMMEDIATE 'DROP TABLE '||r.TABLE_NAME||' CASCADE CONSTRAINTS PURGE';
  END LOOP;
END;
/

-- ---------- [0.2] ลบ SEQUENCE ของโปรเจกต์นี้ (ถ้ามี) ----------
BEGIN
  FOR s IN (SELECT SEQUENCE_NAME FROM USER_SEQUENCES
            WHERE SEQUENCE_NAME IN ('SEQ_USERS','SEQ_VEHICLE','SEQ_BELL_REQ',
                                    'SEQ_DIG_SIGNAL','SEQ_ALERT_STAT','SEQ_IOT_BOX',
                                    'SEQ_BUTTON')) LOOP
    EXECUTE IMMEDIATE 'DROP SEQUENCE '||s.SEQUENCE_NAME;
  END LOOP;
END;
/

-- ---------- [0.3] ลบ VIEW รายงานของโปรเจกต์นี้ (ถ้ามี) ----------
BEGIN
  FOR v IN (SELECT VIEW_NAME FROM USER_VIEWS WHERE VIEW_NAME = 'VW_BELL_REPORT') LOOP
    EXECUTE IMMEDIATE 'DROP VIEW '||v.VIEW_NAME;
  END LOOP;
END;
/
  • FOR r IN (SELECT ...) = วนทีละชื่อที่เจอ · EXECUTE IMMEDIATE 'DROP TABLE ...' = สั่ง SQL ที่ประกอบขึ้นระหว่างรัน (Dynamic SQL) — จำเป็นเพราะชื่อตารางมาจากผล SELECT พิมพ์ DROP ตายตัวไม่ได้
  • CASCADE CONSTRAINTS PURGE — ลบ FK ที่ชี้มาทิ้งพร้อมกัน ไม่ต้องกังวลลำดับลูก-แม่ + ไม่เก็บ recycle bin (สร้างชื่อซ้ำได้ทันที)
  • พูดใน demo: "ผมลบเฉพาะตารางของโปรเจกต์นี้ตามชื่อ เพื่อไม่กระทบตารางงานอื่นใน User เดียวกัน — รันซ้ำกี่ครั้งก็ได้ เพราะถ้าไม่เจอชื่อ ลูปจะไม่วน"

🏗️ ขั้นที่ 1 — CREATE ตารางทีละใบ (ไฟล์ 1 · DDL)

ชื่อ Constraint ทั้งหมดตั้งแบบ PK_/FK_/UQ_/CK_ + ตาราง เพื่ออ่านผล script ตรวจสอบ (ไฟล์ 5) ได้ง่าย

1. USER_TYPE — ประเภทผู้ใช้ (เล็กสุด ใช้เป็นตัวอย่างอ่านทีละบรรทัด)

-- USER TYPE : ประเภทผู้ใช้   [N]---มี---[1]
CREATE TABLE USER_TYPE (
  ROLE_ID    NUMBER(4)     NOT NULL,        -- IDบทบาท (PK)
  ROLE_NAME  VARCHAR2(20)  NOT NULL,        -- ชื่อบทบาท
  CONSTRAINT PK_USER_TYPE      PRIMARY KEY (ROLE_ID),
  CONSTRAINT CK_USER_TYPE_NAME CHECK (ROLE_NAME IN ('ADMIN','DRIVER','PASSENGER')),
  CONSTRAINT UQ_USER_TYPE_NAME UNIQUE (ROLE_NAME)
);
บรรทัดโค้ดแปลเป็นไทยล้วน
CREATE TABLE USER_TYPE ("สร้างตารางใหม่ชื่อ USER_TYPE"
ROLE_ID NUMBER(4) NOT NULL,คอลัมน์รหัสบทบาท เลข ≤ 4 หลัก ห้ามว่าง
ROLE_NAME VARCHAR2(20) NOT NULL,คอลัมน์ชื่อบทบาท ข้อความ ≤ 20 ตัว ห้ามว่าง
CONSTRAINT PK_USER_TYPE PRIMARY KEY (ROLE_ID),ROLE_ID = รหัสประจำตัวของแถว (ไม่ซ้ำ ไม่ว่าง)
CONSTRAINT CK_USER_TYPE_NAME CHECK (...IN ('ADMIN','DRIVER','PASSENGER')),ชื่อบทบาทต้องเป็น 1 ใน 3 ค่านี้เท่านั้น (พิมพ์อื่น DB ปฏิเสธ)
CONSTRAINT UQ_USER_TYPE_NAME UNIQUE (ROLE_NAME)ชื่อบทบาทห้ามซ้ำ (DRIVER มีได้แถวเดียว)

💡 อ่านตารางอื่นใช้โครงนี้ทั้งหมด — คอลัมน์ + ชนิด + NOT NULL + Constraint ชื่อ PK_/CK_/UQ_/FK_

2. USERS — ผู้ใช้งาน (PHONE = ตัวระบุคน)

-- USER : ผู้ใช้งาน   [N]---มี---[1] USER_TYPE
CREATE TABLE USERS (
  USER_ID    NUMBER(10)    NOT NULL,        -- IDUSER (PK)
  FULL_NAME  VARCHAR2(150) NOT NULL,        -- ชื่อ-นามสกุล
  PHONE      VARCHAR2(20),                 -- เบอร์โทร
  ROLE_ID    NUMBER(4)     NOT NULL,       -- FK -> USER_TYPE
  CONSTRAINT PK_USERS       PRIMARY KEY (USER_ID),
  CONSTRAINT UQ_USERS_PHONE UNIQUE (PHONE),
  CONSTRAINT FK_USERS_ROLE  FOREIGN KEY (ROLE_ID) REFERENCES USER_TYPE (ROLE_ID)
);
  • UQ_USERS_PHONE — เบอร์โทรไม่ซ้ำ เพราะทั้งระบบใช้เบอร์โทรเป็น "ชื่อธรรมชาติ" หาคน (DML หา USER_ID ด้วย subquery จาก PHONE)
  • FK_USERS_ROLE — ทุกคนต้องมีบทบาทที่มีจริงใน USER_TYPE (กันพิมพ์รหัสบทบาทมั่ว)

3. VEHICLE — รถ (จำนวนคนบนรถ = Derived → ไม่เก็บคอลัมน์)

-- VEHICLE : ข้อมูลรถ / ยานพาหนะ  ("จำนวนคนบนรถ" = Derived Attribute -> ไม่เก็บคอลัมน์)
CREATE TABLE VEHICLE (
  VEHICLE_ID NUMBER(10)    NOT NULL,       -- ID (PK)
  PLATE_NO   VARCHAR2(20)  NOT NULL,       -- ทะเบียน
  ROUTE_NO   VARCHAR2(20)  NOT NULL,       -- สายทางเดินรถ
  CONSTRAINT PK_VEHICLE       PRIMARY KEY (VEHICLE_ID),
  CONSTRAINT UQ_VEHICLE_PLATE UNIQUE (PLATE_NO)
);
  • จุดอภิปรายของอาจารย์: "จำนวนคนบนรถ" อยู่ใน ER เป็น Derived Attribute (วงรีเส้นประ) — ไม่เก็บคอลัมน์ เพราะค่าคำนวณได้จากตัวนับ IoT/แอปคนขับ ถ้าเก็บจะ stale (ไม่ตรงจริงเสมอ)

4. BELL_REQUEST — การกดกริ่งลง (มี Attribute กำกับความสัมพันธ์)

-- BELL_REQUEST : การส่งสัญญาณกดกริ่งลง   USER [1]---กดกริ่ง---[N]
CREATE TABLE BELL_REQUEST (
  BELL_REQ_ID   NUMBER(12)   NOT NULL,      -- ID (PK)
  USER_ID       NUMBER(10)   NOT NULL,      -- FK -> USERS
  REQ_TIME      DATE         NOT NULL,      -- DATE TIME
  NOTIFY_STATUS VARCHAR2(12) DEFAULT 'SENDING' NOT NULL,  -- สถานะแจ้งเตือน
  ALIGHT_TIME   DATE,                       -- เวลาลง (แอตทริบิวต์กำกับความสัมพันธ์ "กดกริ่ง")
  CONSTRAINT PK_BELL_REQUEST PRIMARY KEY (BELL_REQ_ID),
  CONSTRAINT CK_BELL_STATUS  CHECK (NOTIFY_STATUS IN ('SENDING','SUCCESS','CANCELLED')),
  CONSTRAINT FK_BELL_USER    FOREIGN KEY (USER_ID) REFERENCES USERS (USER_ID)
);
  • ชีวิตของกริ่ง 3 สถานะ: SENDING (กดแล้วรอคนขับยืนยัน) → SUCCESS (ลงแล้ว) หรือ CANCELLED (ยกเลิก) — CHECK ครอบทั้ง 3 ค่า
  • DEFAULT 'SENDING' — กดใหม่ไม่ต้องระบุสถานะ ได้ SENDING อัตโนมัติ
  • ALIGHT_TIME — ตาม ER เป็นวงรีแขวนที่ Relationship "กดกริ่ง" (Attribute กำกับความสัมพันธ์) จึงเก็บในตารางนี้ ไม่ใช่ใน USERS หรือ VEHICLE

5. DIGITAL_BELL_SIGNAL — การส่งสัญญาณไปกริ่งดิจิตอล

-- DIGITAL_BELL_SIGNAL : การส่งสัญญาณไปกริ่งดิจิตอล   USER [1]---กดกริ่ง---[N]
CREATE TABLE DIGITAL_BELL_SIGNAL (
  SIGNAL_ID   NUMBER(12)  NOT NULL,          -- ID (PK)
  USER_ID     NUMBER(10)  NOT NULL,          -- FK -> USERS
  SIGNAL_DATE DATE        NOT NULL,          -- DATE
  CONSTRAINT PK_DIG_SIGNAL PRIMARY KEY (SIGNAL_ID),
  CONSTRAINT FK_DIG_USER   FOREIGN KEY (USER_ID) REFERENCES USERS (USER_ID)
);
  • โครงเดียวกับ BELL_REQUEST แต่ง่ายกว่า (ไม่มีสถานะ/เวลาลง) — เก็บ "ครั้งที่ส่งสัญญาณไปกริ่งดิจิตอลของแต่ละคน" แล้วจับคู่รถผ่าน junction ด้านล่าง

6–7. Junction Tables ×2 — ตารางกลางของ N:M ⭐

-- VEHICLE_BELL_REQUEST : [N:M] "ส่งสัญญาณ" -> Junction Table
CREATE TABLE VEHICLE_BELL_REQUEST (
  BELL_REQ_ID NUMBER(12) NOT NULL,
  VEHICLE_ID  NUMBER(10) NOT NULL,
  SENT_AT     DATE       DEFAULT SYSDATE NOT NULL,
  CONSTRAINT PK_VEH_BELL_REQ PRIMARY KEY (BELL_REQ_ID, VEHICLE_ID),
  CONSTRAINT FK_VBR_BELLREQ  FOREIGN KEY (BELL_REQ_ID) REFERENCES BELL_REQUEST (BELL_REQ_ID),
  CONSTRAINT FK_VBR_VEHICLE  FOREIGN KEY (VEHICLE_ID)  REFERENCES VEHICLE (VEHICLE_ID)
);

-- VEHICLE_DIGITAL_SIGNAL : [N:M] "ส่งสัญญาณ" -> Junction Table
CREATE TABLE VEHICLE_DIGITAL_SIGNAL (
  SIGNAL_ID  NUMBER(12) NOT NULL,
  VEHICLE_ID NUMBER(10) NOT NULL,
  SENT_AT    DATE       DEFAULT SYSDATE NOT NULL,
  CONSTRAINT PK_VEH_DIG_SIG PRIMARY KEY (SIGNAL_ID, VEHICLE_ID),
  CONSTRAINT FK_VDS_SIGNAL  FOREIGN KEY (SIGNAL_ID)  REFERENCES DIGITAL_BELL_SIGNAL (SIGNAL_ID),
  CONSTRAINT FK_VDS_VEHICLE FOREIGN KEY (VEHICLE_ID) REFERENCES VEHICLE (VEHICLE_ID)
);
  • PK = คู่ FK ทั้งสอง (composite) — ตอบ "ทำไม Junction Table": ความสัมพันธ์ N:M แปลงเป็นตารางกลาง 1 แถว = 1 คู่ (กริ่งนี้ → รถนี้) + SENT_AT เป็นข้อมูลของความสัมพันธ์
  • สายสัญญาณแยก 2 ทาง (กดกริ่งผ่านแอป / กริ่งดิจิตอล) เพราะข้อมูลต่างกัน (REQ_TIME + สถานะ vs SIGNAL_DATE)

8. ALERT_STATISTICS — สถิติต่อรถต่อวัน (คู่กับ MERGE)

-- ALERT_STATISTICS : บันทึกสถิติการแจ้งเตือน   VEHICLE [1]---มี---[N]
CREATE TABLE ALERT_STATISTICS (
  STAT_ID     NUMBER(12) NOT NULL,
  VEHICLE_ID  NUMBER(10) NOT NULL,
  STAT_DATE   DATE       NOT NULL,
  ALERT_COUNT NUMBER(8)  DEFAULT 0 NOT NULL,
  CONSTRAINT PK_ALERT_STAT  PRIMARY KEY (STAT_ID),
  CONSTRAINT UQ_ALERT_VDATE UNIQUE (VEHICLE_ID, STAT_DATE),
  CONSTRAINT FK_ALERT_VEH   FOREIGN KEY (VEHICLE_ID) REFERENCES VEHICLE (VEHICLE_ID)
);
  • UNIQUE (VEHICLE_ID, STAT_DATE) — รถ 1 คัน วันเดียว มีสถิติ แถวเดียว — เป็นกฎที่ทำให้ MERGE (Upsert) ใช้ได้: มีแถวแล้ว → UPDATE +1, ยังไม่มี → INSERT 1 (ดูหน้า PL/SQL)

9. IOT_BOX — Weak Entity (composite PK) ⭐

-- IOT_BOX : กล่อง IoT (Weak Entity, Identifying Relationship)   VEHICLE [1]---มี---[N]
-- PK แบบ Composite = PK ของเจ้าของ + Partial Key ตามกฎ Weak Entity
CREATE TABLE IOT_BOX (
  VEHICLE_ID   NUMBER(10)  NOT NULL,        -- PK ของเจ้าของ (รถ)
  BOX_ID       NUMBER(10)  NOT NULL,        -- ID (Partial Key)
  LATITUDE     NUMBER(10,7),                -- พิกัด (lat)
  LONGITUDE    NUMBER(10,7),                -- พิกัด (lng)
  LAST_PING_AT DATE,
  CONSTRAINT PK_IOT_BOX     PRIMARY KEY (VEHICLE_ID, BOX_ID),
  CONSTRAINT FK_IOT_VEHICLE FOREIGN KEY (VEHICLE_ID) REFERENCES VEHICLE (VEHICLE_ID)
);
  • ตอบเด็ดขาด: "ทำไม PK เป็น (VEHICLE_ID, BOX_ID)?" — กล่อง IoT เป็น Weak Entity ผูกกับรถแบบ Identifying Relationship → PK = PK เจ้าของ + Partial Key · BOX_ID รถ A กับรถ B ซ้ำกันได้ แต่ในรถเดียวกันซ้ำไม่ได้
  • พิกัด NUMBER(10,7) = ทศนิยม 7 ตำแหน่ง (ละเอียดระดับเซนติเมตร) + LAST_PING_AT = ตำแหน่งล่าสุดของรถ (ตอบ UC ดูตำแหน่งรถ)

10–11. BELL_BUTTON + VEHICLE_BELL_BUTTON — ปุ่มกริ่ง N:M "มี"

-- BELL_BUTTON : ปุ่มกดแจ้งเตือน   VEHICLE [N:M]---มี
CREATE TABLE BELL_BUTTON (
  BUTTON_ID    NUMBER(10) NOT NULL,
  BUTTON_LABEL VARCHAR2(50),
  CONSTRAINT PK_BELL_BUTTON PRIMARY KEY (BUTTON_ID)

  VEHICLE_ID   NUMBER(10) NOT NULL,
  BUTTON_ID    NUMBER(10) NOT NULL,
  INSTALLED_AT DATE       DEFAULT SYSDATE NOT NULL,
  CONSTRAINT PK_VEH_BELL_BTN PRIMARY KEY (VEHICLE_ID, BUTTON_ID),
  CONSTRAINT FK_VBB_VEHICLE  FOREIGN KEY (VEHICLE_ID) REFERENCES VEHICLE (VEHICLE_ID),
  CONSTRAINT FK_VBB_BUTTON   FOREIGN KEY (BUTTON_ID)  REFERENCES BELL_BUTTON (BUTTON_ID)
);
  • ปุ่มเดียวติดได้หลายรถ · รถเดียวมีหลายปุ่ม → N:M → Junction + INSTALLED_AT (ติดตั้งเมื่อไร) เป็นข้อมูลของความสัมพันธ์

เทคนิค 3 อย่างในไฟล์นี้ (โดนถามได้)

ALTER SESSION SET NLS_DATE_FORMAT = 'DD/MM/YYYY HH24:MI:SS';
  • ① ปรับรูปแบบวันที่ของ session — พิมพ์วันที่แบบวัน/เดือน/ปี ชั่วโมง:นาที:วินาที ได้ตลอดไฟล์ (เป็นค่าต่อ session เท่านั้น ไม่กระทบคนอื่น)
  • ② FK อ้างด้วย subquery ตาม natural key — ไม่ hard-code เลข ID:
INSERT INTO USERS (USER_ID, FULL_NAME, PHONE, ROLE_ID) VALUES
  (SEQ_USERS.NEXTVAL, 'สมหญิง เดินทาง', '0800000003',
   (SELECT ROLE_ID FROM USER_TYPE WHERE ROLE_NAME = 'PASSENGER'));
  • อ่านว่า: "สร้างผู้ใช้ใหม่ รหัสจากเครื่องนับ ชื่อ สมหญิง เบอร์ 0800000003 บทบาท = หารหัสของบทบาทชื่อ PASSENGER มาเอง" — ถ้าเลข ROLE_ID เปลี่ยนในอนาคต สคริปต์ไม่พัง (ดีกว่าพิมพ์ 3 ตรง ๆ)
  • ③ วันที่ใช้ TO_DATE เสมอ — TO_DATE('10/11/2026 08:15:00','DD/MM/YYYY HH24:MI:SS') = "สตริงนี้คือวันที่ตามรูปแบบนี้" — กันปัญหา locale สลับวัน/เดือน

natural key — คอลัมน์ที่โลกจริงใช้ระบุของอยู่แล้ว (เบอร์โทร, ทะเบียนรถ, ชื่อบทบาท) ต่างจาก surrogate key (เลขจาก SEQUENCE) ที่มีไว้เพื่อ DB — DML นี้ใช้ natural key "หา" surrogate key ด้วย subquery ทุกครั้ง

Q ทำไม IOT_BOX ถึงมี PK เป็น (VEHICLE_ID, BOX_ID) แบบ composite?

เฉลย: กฎ Weak Entity — กล่องไม่มีตัวตนอิสระนอกรถเจ้าของ รหัสกล่องจึงสมบูรณ์เมื่อผูกกับรหัสรถ (BOX_ID คนละรถซ้ำกันได้ แต่รถเดียวกันซ้ำไม่ได้)

Q "จำนวนคนบนรถ" ใน ER ทำไมไม่มีคอลัมน์ในตาราง VEHICLE?
