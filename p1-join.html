① อาจารย์ต้องการอะไร (โจทย์ข้อนี้)

"3- เขียน SQL : JOIN แสดงข้อมูลการทำงานหลัก ( JOIN ตารางมากๆ)" — โจทย์เน้นคำว่า JOIN ตารางมาก ๆ — ทุกข้อต้องตอบคำถามธุรกิจจริงของระบบ (ไม่ใช่ SELECT * จากตารางเดียว) และอาจารย์มักจิ้มถามว่า "JOIN อะไรกับอะไร ทำไมต้อง LEFT JOIN ข้อนี้" — เตรียมคำตอบทุกข้อตามที่อธิบายด้านล่าง

JOIN (INNER) — ดึงเฉพาะแถวที่ "เจอกันทั้งสองตาราง" — ใช้เมื่อข้อมูลต้องมีคู่เสมอ

LEFT JOIN — แถวฝั่งซ้ายอยู่ครบเสมอ ฝั่งขวาไม่เจอจะเติม NULL — ใช้เมื่อ "ไม่มีก็ต้องโผล่" เช่น เอกสารที่ยังไม่ถูกพิจารณา, คนที่ยังไม่ยืนยัน

CROSS JOIN — ผลคูณทุกแถว ใช้เมื่อต้องการ "ชุดเป้าหมายอ้างอิง" ทั้งหมดเทียบกับสิ่งที่ทำแล้ว

Aggregate + GROUP BY — COUNT/SUM/MIN รวมแถวเป็นตัวเลขต่อกลุ่ม · กรองหลังรวมด้วย HAVING (กรองก่อนรวมใช้ WHERE)

🌱 ห้องทดลอง JOIN จิ๋ว — เห็นผลก่อนอ่านโค้ดจริง (3 นาที ข้อมูลจริงจากไฟล์ 02)

JOIN = "นำ 2 ตารางมาต่อกันด้วยคอลัมน์ที่เป็นคู่กัน" — ด้วยข้อมูลจริงของเรา (หลังเดิน Flow ทดสอบครบ 1 รอบตามหน้า PL/SQL):

ตาราง DOCUMENTS (ฝั่งซ้าย — เอกสาร 4 ฉบับ)
DOC_IDTITLE
5001ประกาศวันหยุดสงกรานต์
5002ข้อความเวียน: ปิดประตู
5003ประกาศนโยบาย WFH
5004เรียนเชิญประชุมไตรมาส
ตาราง APPROVALS (ฝั่งขวา — ผลพิจารณามีแค่ 2 แถว)
DOC_IDDECISIONAPPROVER
5001APPROVEDอรุณ (CEO)
5003REJECTEDมาลี (Manager)

ต่อสองตารางด้วยคอลัมน์คู่ DOC_ID — สังเกตว่า เอกสาร 5002 กับ 5004 ไม่มีผลพิจารณาเลย (ยัง DRAFT/PENDING) — ทางเลือกการต่อมี 2 แบบ:

คำสั่งผลลัพธ์บนจอ (นับแถวให้ดูเลย)
FROM DOCUMENTS d JOIN APPROVALS a ON a.DOC_ID = d.DOC_ID
(INNER JOIN)		ได้ 2 แถว — 5001 กับ 5003 เท่านั้น · 5002/5004 หายไปเงียบ ๆ เพราะไม่มีคู่
FROM DOCUMENTS d LEFT JOIN APPROVALS a ON a.DOC_ID = d.DOC_ID
(LEFT JOIN)		ได้ครบ 4 แถว — 5002/5004 ยังอยู่ แต่ฝั่งขวาเติม NULL (ตีความ: "ยังไม่ถูกพิจารณา")

🧠 จำแบบเด็ก ๆ: JOIN = จับคู่ · INNER = จับคู่ได้ค่อยอยู่ (ไม่มีคู่ทิ้ง) · LEFT = ฝั่งซ้ายอยู่ครบเสมอ ไม่มีคู่ก็ใส่ว่าง

NULL อ่านว่า "ว่าง/ไม่มีข้อมูล" — ไม่ใช่ 0 ไม่ใช่ช่องว่าง — เช็คด้วย IS NULL เท่านั้น ห้ามใช้ = NULL (โจทย์ Q2 ใช้เทคนิคนี้พอดี)

🌱 อ่านคำสั่ง SELECT ยาว ๆ เป็น 7 ขั้น (อ่านผิดลำดับ = งงเปล่า ๆ)

อย่าอ่านโค้ด SELECT จากซ้ายไปขวา! อ่านตามลำดับที่ฐานข้อมูลทำงานจริง — ใช้โค้ด Q3 ของเราเดินทีละขั้นให้เห็นจำนวนแถวจริง:

ขั้นคำสั่งในโค้ดทำอะไรข้อมูลของเรากลายเป็น
1FROM DOCUMENTS dตั้งต้นจากตารางเอกสาร4 แถว (5001–5004)
2LEFT JOIN READ_LOGS lgต่อบันทึกการอ่าน (ไม่มีคู่ก็คงอยู่เป็น NULL)ยัง 4 แถว (5001 มีข้อมูลอ่าน, ที่เหลือ NULL)
3CROSS JOIN ROLES rผสมทุกแถวกับตารางบทบาท (4 บทบาท)4 × 4 = 16 แถว
4JOIN EMPLOYEES e ... WHERE r.ROLE_NAME='EMPLOYEE'ต่อคนของแต่ละบทบาท + คัดเอาเฉพาะบทบาทพนักงาน16 แถว = เอกสาร 4 ฉบับ × พนักงานกลุ่มเป้าหมาย 4 คน
5GROUP BY d.DOC_ID, ...จับกลุ่ม "ต่อ 1 เอกสาร" แล้วนับรวม (COUNT)เหลือ 4 กลุ่ม (กลุ่มละเอกสาร)
6SELECT ... ROUND(...) AS ACK_PCTคำนวณ % แล้วตั้งชื่อคอลัมน์ผลว่า ACK_PCT5001 = 1/4 = 25.0 · ที่เหลือ = 0.0
7ORDER BY d.DOC_IDเรียงผลตามรหัสเอกสารแสดง 5001 → 5004 บนจอ

💡 WHERE/JOIN ทำงาน "ก่อน" รวมคะแนน (GROUP BY) — HAVING ทำงาน "หลัง" — นี่คือเหตุผลที่กรองชนิดเอกสารใช้ WHERE แต่กรอง "เกิน SLA" (ต้องนับเวลาก่อน) ใช้ HAVING

Q1 · ติดตามผลการพิจารณาอนุมัติ (6 ตาราง) ⭐ ตัวเด่นสุดของโจทย์

04_JOIN_QUERIES.sql · Q1 
-- ---------------------------------------------------------------------
-- Q1 (6 ตาราง) : ติดตามผลการพิจารณาอนุมัติ — เอกสาร × ผู้ร่าง × ผู้อนุมัติ × ผล × ลายเซ็น
-- ---------------------------------------------------------------------
SELECT d.DOC_ID,
       d.TITLE,
       d.DOC_TYPE,
       d.STATUS,
       c.EMP_NAME  AS CREATOR_NAME,
       cr.ROLE_NAME AS CREATOR_ROLE,
       ap.EMP_NAME AS APPROVER_NAME,
       a.DECISION,
       a.REASON,
       s.SIGNATURE_HASH,
       s.SIGNED_DATE
FROM   DOCUMENTS d
JOIN   EMPLOYEES c    ON c.EMP_ID = d.CREATED_BY
JOIN   ROLES cr       ON cr.ROLE_ID = c.ROLE_ID
LEFT   JOIN APPROVALS a ON a.DOC_ID = d.DOC_ID
LEFT   JOIN EMPLOYEES ap ON ap.EMP_ID = a.APPROVER_ID
LEFT   JOIN SIGNATURES s ON s.DOC_ID = d.DOC_ID
ORDER  BY d.DOC_ID, a.DECIDED_DATE;
  • เดินลูกโซ่: DOCUMENTS → EMPLOYEES (ผู้ร่าง ผ่าน CREATED_BY) → ROLES (บทบาทผู้ร่าง) — สองตารางนี้ INNER JOIN เพราะทุกเอกสารต้องมีผู้ร่างเสมอ
  • แต่ APPROVALS / SIGNATURES เป็น LEFT JOIN — จุดขายสำคัญ: เอกสารที่ยังเป็น DRAFT/PENDING ยังไม่มีผลพิจารณาและไม่มีลายเซ็น ถ้าใช้ INNER JOIN แถวพวกนี้จะ หายไปเงียบ ๆ — แถว LEFT JOIN ไม่เจอฝั่งขวาจะมีค่า NULL ซึ่งตีความได้ว่า "ยังไม่ถูกพิจารณา"
  • EMPLOYEES ถูก JOIN 2 รอบ (alias c = creator, ap = approver) — อธิบายอาจารย์: "ตารางเดียวแต่ 2 บทบาท ต้องตั้ง alias แยกกัน"

Q2 · ใครยังไม่ยืนยัน — LEFT JOIN + IS NULL (Anti-Join)

04_JOIN_QUERIES.sql · Q2 
-- ---------------------------------------------------------------------
-- Q2 (4 ตาราง) : ใครยังไม่เปิดอ่าน-ยืนยันเอกสาร (LEFT JOIN + IS NULL หาของที่ขาด)
-- ---------------------------------------------------------------------
SELECT d.DOC_ID,
       d.TITLE,
       e.EMP_NAME,
       e.EMAIL,
       n.CHANNEL,
       n.NOTIF_TYPE,
       n.SENT_AT
FROM   DOCUMENTS d
JOIN   NOTIFICATIONS n ON n.DOC_ID = d.DOC_ID
JOIN   EMPLOYEES e     ON e.EMP_ID = n.EMP_ID
LEFT   JOIN READ_LOGS r ON r.DOC_ID = d.DOC_ID AND r.EMP_ID = e.EMP_ID
WHERE  r.LOG_ID IS NULL          -- ยังไม่มีบันทึกอ่าน = ยังไม่ยืนยัน
ORDER  BY d.DOC_ID, e.EMP_ID;
  • จุดเริ่มจาก NOTIFICATIONS (ใครได้รับแจ้งเตือนแล้ว) — คนที่ยังไม่ได้รับแจ้งจะไม่นับ เพราะยังไม่ใช่เขตความรับผิดชอบของ SLA
  • เงื่อนไข 2 คอลัมน์ใน ON ของ LEFT JOIN (r.DOC_ID = d.DOC_ID AND r.EMP_ID = e.EMP_ID) — จับคู่ "คนกับเอกสารเดียวกัน" แล้วค่อยกรอง r.LOG_ID IS NULL = ไม่เจอแถวยืนยัน → นี่คือคนที่ยังไม่ยืนยัน
  • ถ้าย้ายเงื่อนไขลง WHERE แบบ WHERE r.EMP_ID = e.EMP_ID จะกลายเป็น INNER JOIN ทันที (ผล NULL ถูกกรองทิ้ง) — กับดักคลาสสิก อาจารย์ชอบถาม
  • เทียบกับ NOT EXISTS ใน SP_CHECK_SLA_REMIND — สองเทคนิคได้ผลเดียวกัน

Q3 · อัตราการรับทราบต่อเอกสาร (%)

04_JOIN_QUERIES.sql · Q3 
-- ---------------------------------------------------------------------
-- Q3 (5 ตาราง + Aggregate) : อัตราการรับทราบต่อเอกสารเทียบกลุ่มเป้าหมาย
-- ---------------------------------------------------------------------
SELECT d.DOC_ID,
       d.TITLE,
       r.ROLE_NAME AS TARGET_ROLE,
       COUNT(DISTINCT lg.EMP_ID) AS ACK_COUNT,
       COUNT(DISTINCT e.EMP_ID)  AS TARGET_COUNT,
       ROUND(COUNT(DISTINCT lg.EMP_ID) / COUNT(DISTINCT e.EMP_ID) * 100, 1) AS ACK_PCT
FROM   DOCUMENTS d
LEFT   JOIN READ_LOGS lg ON lg.DOC_ID = d.DOC_ID
CROSS  JOIN ROLES r
JOIN   EMPLOYEES e ON e.ROLE_ID = r.ROLE_ID
WHERE  r.ROLE_NAME = 'EMPLOYEE'
GROUP  BY d.DOC_ID, d.TITLE, r.ROLE_NAME,
          (SELECT COUNT(*) FROM EMPLOYEES WHERE ROLE_ID = 4)
ORDER  BY d.DOC_ID;
  • CROSS JOIN ROLES + WHERE r.ROLE_NAME = 'EMPLOYEE' = เลือกชุดเป้าหมาย "พนักงานทุกคน" เป็นตัวหารของ %
  • COUNT(DISTINCT ...) — DISTINCT จำเป็น เพราะ LEFT JOIN READ_LOGS กับ CROSS JOIN ทำให้แถวซ้ำ (คน 1 คนเจอหลายแถว) นับไม่ DISTINCT จะบวม
  • ROUND(..., 1) — ปัดเปอร์เซ็นต์ 1 ตำแหน่ง · ใน Oracle จำนวนเต็มหารจำนวนเต็มค่อยขยายเป็นทศนิยมด้วย * 100
  • กฎ GROUP BY: คอลัมน์ใน SELECT ที่ไม่ได้ถูก aggregate ต้องอยู่ใน GROUP BY เสมอ (d.DOC_ID, d.TITLE, r.ROLE_NAME) — ไฟล์แทรก subquery นับจำนวนพนักงาน role 4 ไว้ใน GROUP BY ด้วยเพื่อเทียบตัวเลขเป้าหมาย

Q4 · เอกสารที่เกิน SLA — HAVING เทียบก่อน/หลังรวม

04_JOIN_QUERIES.sql · Q4 
-- ---------------------------------------------------------------------
-- Q4 (3 ตาราง + Subquery) : เอกสารที่เกิน SLA 24 ชม. ยังยืนยันไม่ครบ
-- ---------------------------------------------------------------------
SELECT d.DOC_ID,
       d.TITLE,
       d.STATUS,
       MIN(n.SENT_AT) AS FIRST_SENT,
       ROUND((SYSDATE - MIN(n.SENT_AT)) * 24, 1) AS ELAPSED_HOURS
FROM   DOCUMENTS d
JOIN   NOTIFICATIONS n ON n.DOC_ID = d.DOC_ID
WHERE  d.DOC_TYPE = 'MEMO'
GROUP  BY d.DOC_ID, d.TITLE, d.STATUS, d.SLA_HOURS
HAVING (SYSDATE - MIN(n.SENT_AT)) * 24 >= MIN(d.SLA_HOURS)
ORDER  BY ELAPSED_HOURS DESC;
  • WHERE vs HAVING (โดนถามแน่): WHERE กรองแถวดิบ ก่อน GROUP BY (เอาเฉพาะ MEMO) · HAVING กรอง "กลุ่มหลังรวมแล้ว" เพราะเงื่อนไขใช้ aggregate MIN()
  • MIN(d.SLA_HOURS) ใน HAVING = เอา SLA ของเอกสารแต่ละฉบับมาเทียบ (ไม่ hard-code 24) — ยืดหยุ่นตามที่ธุรการตั้งใน UC04
  • (SYSDATE - MIN(n.SENT_AT)) * 24 — วันลบวันใน Oracle = จำนวนวันแบบทศนิยม คูณ 24 = ชั่วโมงที่ผ่านไป
  • เรียง ELAPSED_HOURS DESC = เกินกว่ามากสุดขึ้นก่อน — ใช้เป็นรายงาน "ต้องเร่งแจ้งซ้ำตัวไหนก่อน"

Q5 · Audit Trail — อ่าน Log ที่ Trigger เขียน

04_JOIN_QUERIES.sql · Q5 
-- ---------------------------------------------------------------------
-- Q5 (4 ตาราง) : ประวัติการเปลี่ยนสถานะเอกสาร (Audit Trail จาก Trigger)
-- ---------------------------------------------------------------------
SELECT d.DOC_ID,
       d.TITLE,
       lg.OLD_STATUS,
       lg.NEW_STATUS,
       lg.CHANGED_DATE
FROM   DOC_STATUS_LOG lg
JOIN   DOCUMENTS d ON d.DOC_ID = lg.DOC_ID
ORDER  BY lg.DOC_ID, lg.CHANGED_DATE;
  • ตารางหลักคือ DOC_STATUS_LOG (ข้อมูลที่ Trigger TRG_DOC_STATUS_LOG เขียนอัตโนมัติ) แล้ว JOIN DOCUMENTS เอาชื่อเอกสารมาแสดง
  • เล่าให้อาจารย์ฟังเป็นเรื่อง: "รัน SP_DECIDE_APPROVAL แล้วมาเปิดข้อนี้ จะเห็นสายสถานะ DRAFT → PENDING → APPROVED → SIGNED → DISTRIBUTED ครบทุกจุด เป็นหลักฐาน Audit ตาม UC03"

Q6 · สิทธิ์เข้าถึงของพนักงาน (Access Matrix)

04_JOIN_QUERIES.sql · Q6 
-- ---------------------------------------------------------------------
-- Q6 (4 ตาราง) : สิทธิ์การเข้าถึงของพนักงานแต่ละคน (Access Matrix × Role × Employee × Dept)
-- ---------------------------------------------------------------------
SELECT e.EMP_NAME,
       dept.DEPT_NAME,
       r.ROLE_NAME,
       a.DOC_TYPE,
       a.CAN_VIEW
FROM   EMPLOYEES e
JOIN   DEPARTMENTS dept ON dept.DEPT_ID = e.DEPT_ID
JOIN   ROLES r ON r.ROLE_ID = e.ROLE_ID
JOIN   ACCESS_MATRIX a ON a.ROLE_ID = r.ROLE_ID
ORDER  BY e.EMP_ID, a.DOC_TYPE;
  • JOIN ลูกโซ่ 4 ตารางแบบมาตรฐาน: พนักงาน → แผนก → บทบาท → แถวสิทธิ์ของบทบาทนั้น — ผลออกมาเป็น "ใคร อยู่ไหน มี role อะไร เห็นเอกสารประเภทไหน"
  • ตอบ UC08 (กำหนดสิทธิ์) — อาจารย์ถาม "สิทธิ์เก็บที่ไหน" ตอบ: ตาราง ACCESS_MATRIX ผ่าน ROLE_ID ของ EMPLOYEES

Q ใน Q1 ทำไม APPROVALS ต้อง LEFT JOIN ไม่ใช่ JOIN ธรรมดา?
