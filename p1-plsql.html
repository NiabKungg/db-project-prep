① อาจารย์ต้องการอะไร (โจทย์ข้อนี้)

"2- เขียน PL/SQL ตามโจทย์หลักของระบบงาน (Transaction Processing)" — แปลว่าโค้ดต้องครอบการทำงานหลักจริงของระบบ (ส่งอนุมัติ → อนุมัติ/ตีกลับ → ลงนาม → กระจาย → ยืนยัน → เตือน SLA) และทุกขั้นต้องประกาศได้ว่า Transaction อยู่ตรงไหน · เมื่อไร COMMIT · เมื่อไร ROLLBACK · จับ error ยังไง — ไม่ใช่เขียน SP เพื่อโชว์ว่ารันได้เฉย ๆ

🧠 พื้นฐานที่ต้องพูดให้ออกก่อนรันโค้ด

Transaction คืออะไร — แล้วเกี่ยวกับ Atomicity ยังไง

Transaction = ชุดคำสั่งที่ต้อง "สำเร็จทั้งหมดหรือไม่สำเร็จทั้งหมด" (All-or-Nothing = คุณสมบัติ Atomicity ของ ACID) — ในระบบนี้ SP_DECIDE_APPROVAL คือ Transaction ขนาดใหญ่ที่สุด: บันทึกผลพิจารณา + ลงนาม + กระจายหลายช่องทาง + แจ้งเตือนทุกคน — ถ้าตายกลางทางขั้นไหน ROLLBACK จะย้อนทุกอย่างกลับ ข้อมูลไม่มีวันเป็น "ครึ่ง ๆ กลาง ๆ" เช่น ลงนามแล้วแต่ไม่กระจาย

PROCEDURE — โปรแกรมเก็บในฐานข้อมูล เรียกใช้ด้วย EXEC SP_XXX(...) — เป็นที่ที่ Transaction ถูกเขียนเป็นชุดเดียว

TRIGGER — โปรแกรมที่ฐานข้อมูล "ยิงเองอัตโนมัติ" เมื่อเกิดเหตุการณ์ (เช่น หลัง UPDATE คอลัมน์ STATUS) — เราไม่เรียกมันเอง

FOR UPDATE — ล็อกแถวที่ SELECT ไว้จนจบ Transaction กันคนอื่นแก้ทับขณะเรากำลังตัดสินใจ (Concurrency Control)

RAISE_APPLICATION_ERROR(-20001, '...') — โยน error ของเราเอง (ช่วงเลข -20000 ถึง -20999) พร้อมข้อความไทยให้ผู้ใช้เข้าใจ

🌱 อ่านโครง PROCEDURE แบบมือใหม่ (รู้โครง = อ่านทุกตัวในหน้านี้ได้)

Procedure ทั้ง 4 ตัวของ Part I (และทั้ง 5 ตัวของ Part II) เขียนในโครงเดียวกันเป๊ะ — จำโครง 4 ชั้นนี้แล้วอ่านโค้ดเป็นภาษาไทยได้เลย:

CREATE OR REPLACE PROCEDURE ชื่อ (ค่าที่ส่งเข้า IN ..., ค่าที่ได้กลับ OUT ...) IS
    -- ชั้น 1: ประกาศตัวแปร (กระดาษทดของเรา)
BEGIN
    -- ชั้น 2: ทำงานตามลำดับบนลงล่าง (อ่าน, เช็คเงื่อนไข, เขียนข้อมูล)
    -- ชั้น 2 จบด้วย COMMIT ถ้าสำเร็จทุกขั้น
EXCEPTION
    -- ชั้น 3: จับ error — พังกลางทาง → ROLLBACK (ย้อนทุกอย่าง)
END;
/
  • ชั้น 1 (ประกาศตัวแปร) — เช่น V_STATUS VARCHAR2(12) = "กล่องเก็บค่าชั่วคราว 1 ใบ ชื่อ V_STATUS ใส่ข้อความได้ ≤12 ตัว" (V = ตัวแปรของเรา ไม่ใช่คอลัมน์ตาราง)
  • ชั้น 2 (BEGIN) — อ่านคำสั่งเป็นประโยคเล่าเรื่อง: SELECT ... INTO V_STATUS = "ดึงค่าจากตารางมาเก็บในกล่อง" (ต้องได้แถวเดียวเท่านั้น — ไม่เจอแถวเลยจะโยน NO_DATA_FOUND) · IF ... THEN = ตรวจเงื่อนไข · INSERT/UPDATE = เขียนข้อมูล · COMMIT = บันทึกถาวร
  • ชั้น 3 (EXCEPTION) — "ถ้าเกิดปัญหาอะไรล่ะ?": WHEN ชนิดปัญหา THEN วิธีจัดการ — ทุกตัวในเว็บนี้ตอบเหมือนกัน: ROLLBACK ก่อนเสมอ แล้วค่อยแจ้งข้อความให้ผู้ใช้เข้าใจ
  • เรียกใช้: EXEC SP_SUBMIT_DOC(5001); = "รัน Procedure ชื่อนี้ โดยส่งค่า 5001 เข้าช่อง P_DOC_ID" — ตัวเลข 5001 คือรหัสเอกสารที่ใส่ไว้ตอน DML (จำตัวเลขที่หน้า DML เตรียมไว้ให้พอดี)
  • IN / OUT — IN = ช่องใส่ค่าเข้ามา · OUT = ช่องที่ Procedure ใส่ค่าคืนให้เรา (เจอชัด ๆ ที่ SP_LOGIN ของ Part II ซึ่งคืน USER_ID/บทบาท/ชื่อ)

ก้อนที่ 1 · TRIGGER — Audit Trail อัตโนมัติ

03_PLSQL.sql · TRIGGER 
-- ---------- TRIGGER : บันทึก Audit Trail ทุกครั้งที่สถานะเปลี่ยน (ผ่าน Doc Status Log) ----------
CREATE OR REPLACE TRIGGER TRG_DOC_STATUS_LOG
AFTER UPDATE OF STATUS ON DOCUMENTS
FOR EACH ROW
WHEN (OLD.STATUS <> NEW.STATUS)
BEGIN
    INSERT INTO DOC_STATUS_LOG (LOG_ID, DOC_ID, OLD_STATUS, NEW_STATUS, CHANGED_DATE)
    VALUES (SEQ_LOG.NEXTVAL, :NEW.DOC_ID, :OLD.STATUS, :NEW.STATUS, SYSDATE);
END;
/
  • AFTER UPDATE OF STATUS ON DOCUMENTS — ยิงเฉพาะเมื่อ UPDATE โดนคอลัมน์ STATUS (ไม่ใช่ทุก UPDATE)
  • FOR EACH ROW — ทำงานราวแถว (ถ้า UPDATE 10 แถวก็ยิง 10 ครั้ง)
  • WHEN (OLD.STATUS <> NEW.STATUS) — บันทึกเฉพาะ "ค่าเปลี่ยนจริง" กัน Log เปื่อยจากการ UPDATE ค่าเดิมทับ
  • :OLD.STATUS / :NEW.STATUS — ค่าก่อน/หลังของแถวที่ถูกแก้ — นี่คือ "Audit Trail": ใครดูย้อนหลังว่าเอกสารผ่านสถานะอะไรมาแล้ว ตอบ UC03 และกฎ BR-Memo-103 (ห้ามแก้ Log)
  • พูดใน demo: "Trigger ทำงานอัตโนมัติ เราไม่ต้องเรียก — สมมติระบบลืมเขียน log เอง ฐานข้อมูลก็ยังจับได้ครบ"

ก้อนที่ 2 · SP_SUBMIT_DOC — ส่งร่างเสนออนุมัติ

03_PLSQL.sql · PROCEDURE 1 
-- ---------- PROCEDURE 1 : ส่งร่างเอกสารเข้าสู่กระบวนการอนุมัติ ----------
CREATE OR REPLACE PROCEDURE SP_SUBMIT_DOC (P_DOC_ID IN NUMBER) IS
    V_STATUS VARCHAR2(12);
BEGIN
    SELECT STATUS INTO V_STATUS FROM DOCUMENTS WHERE DOC_ID = P_DOC_ID FOR UPDATE;

    IF V_STATUS NOT IN ('DRAFT','REJECTED') THEN
        RAISE_APPLICATION_ERROR(-20001,
            'เอกสารนี้ไม่อยู่ในสถานะร่าง จึงส่งเสนออนุมัติไม่ได้ (สถานะปัจจุบัน: ' || V_STATUS || ')');
    END IF;

    UPDATE DOCUMENTS SET STATUS = 'PENDING' WHERE DOC_ID = P_DOC_ID;
    COMMIT;   -- Transaction สำเร็จครบทุกขั้นจึง COMMIT
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20002, 'ไม่พบเอกสารรหัส ' || P_DOC_ID);
    WHEN OTHERS THEN
        ROLLBACK;   -- ผิดพลาดกลางทาง = ย้อนทุกอย่างกลับ (Atomicity)
        RAISE;
END;
/
  • อ่านสถานะก่อน พร้อมล็อกแถวด้วย FOR UPDATE — กันกรณีสองคนกด "ส่งอนุมัติ" เอกสารเดียวกันพร้อมกัน
  • ยอมรับเฉพาะ DRAFT หรือ REJECTED — ตรง Flow: ร่างใหม่ หรือ ร่างที่ถูกตีกลับ (UC06) ส่งได้ · ถ้าสถานะอื่น (เช่น PENDING อยู่แล้ว) raise -20001 — นี่คือ error ที่ demo โชว์
  • ผ่าน → UPDATE เป็น PENDING แล้ว COMMIT — ยิง Trigger เขียน log DRAFT→PENDING อัตโนมัติด้วย
  • NO_DATA_FOUND = SELECT INTO ไม่เจอแถว (รหัสเอกสารผิด) → ROLLBACK + raise -20002 · WHEN OTHERS = ทุก error อื่น → ROLLBACK แล้ว RAISE ส่งต่อให้ผู้เรียกเห็น error จริง

🌱 ไล่อ่าน SP_SUBMIT_DOC ทีละบรรทัด (แปลเป็นไทยล้วน — ตัวเล็กที่สุด เข้าใจง่ายสุด อ่านแล้วไปต่อได้ทุกก้อน)

💡 สูตรอ่านเท่านี้: "รับค่า → ล็อกแถว → เช็คเงื่อนไข (ผิดแล้วโยน error) → เขียนข้อมูล → COMMIT → พังแล้ว ROLLBACK" — โครงนี้ซ้ำทั้ง 4 ตัวของ Part I และ 5 ตัวของ Part II ต่างกันแค่เงื่อนไขธุรกิจข้างใน

ก้อนที่ 3 · SP_DECIDE_APPROVAL — Transaction ใหญ่สุดของระบบ (XOR + AND) ⭐

03_PLSQL.sql · PROCEDURE 2 
-- ---------- PROCEDURE 2 : พิจารณาอนุมัติ/ตีกลับ (XOR Gateway ของระบบจริง) ----------
CREATE OR REPLACE PROCEDURE SP_DECIDE_APPROVAL (
    P_DOC_ID    IN NUMBER,
    P_APPROVER  IN NUMBER,
    P_DECISION  IN VARCHAR2,
    P_REASON    IN VARCHAR2
) IS
    V_CREATOR  NUMBER;
    V_DOCTYPE  VARCHAR2(15);
    V_PRIORITY VARCHAR2(10);
    V_CHANNELS SYS.ODCIVARCHAR2LIST := SYS.ODCIVARCHAR2LIST();
    V_EMP      NUMBER;
BEGIN
    -- ตรวจสอบผู้พิจารณาต้องมีบทบาท APPROVER เท่านั้น (ตาม Lane CEO/Manager)
    SELECT COUNT(*) INTO V_CREATOR
    FROM EMPLOYEES WHERE EMP_ID = P_APPROVER AND ROLE_ID = 3;
    IF V_CREATOR = 0 THEN
        RAISE_APPLICATION_ERROR(-20003, 'ผู้พิจารณาต้องมีบทบาท Approver เท่านั้น');
    END IF;

    SELECT CREATED_BY, DOC_TYPE, PRIORITY INTO V_CREATOR, V_DOCTYPE, V_PRIORITY
    FROM DOCUMENTS WHERE DOC_ID = P_DOC_ID FOR UPDATE;

    -- บันทึกผลการพิจารณา
    INSERT INTO APPROVALS (APPROVAL_ID, DOC_ID, APPROVER_ID, DECISION, REASON, DECIDED_DATE)
    VALUES (SEQ_APPROVAL.NEXTVAL, P_DOC_ID, P_APPROVER, P_DECISION, P_REASON, SYSDATE);

    IF P_DECISION = 'REJECTED' THEN
        -- ตีกลับให้ธุรการแก้ไข (กลับเข้าสู่สถานะร่าง) — DR-Ann-101
        UPDATE DOCUMENTS SET STATUS = 'REJECTED' WHERE DOC_ID = P_DOC_ID;
    ELSE
        -- ผ่าน → ลงนามอิเล็กทรอนิกส์ (ห้ามเผยแพร่ก่อนลงนาม = BR-Ann-102)
        UPDATE DOCUMENTS SET STATUS = 'APPROVED' WHERE DOC_ID = P_DOC_ID;
        INSERT INTO SIGNATURES (SIGN_ID, DOC_ID, SIGNER_ID, SIGNATURE_HASH, SIGNED_DATE)
        VALUES (SEQ_SIGN.NEXTVAL, P_DOC_ID, P_APPROVER,
                'SHA256-' || P_DOC_ID || '-' || TO_CHAR(SYSDATE,'YYYYMMDDHH24MISS'), SYSDATE);
        UPDATE DOCUMENTS SET STATUS = 'SIGNED' WHERE DOC_ID = P_DOC_ID;

        -- AND Gateway ขา 1 : จัดเก็บ + ออกรหัสอ้างอิง (Doc ID = รหัสเอกสารระบบ)
        UPDATE DOCUMENTS SET STATUS = 'SIGNED' WHERE DOC_ID = P_DOC_ID;  -- สถานะคงอยู่ รอกระจาย

        -- AND Gateway ขา 2 : กระจายตามความเร่งด่วน (OR Channel)
        -- DR: EMERGENCY → EMAIL+APP+SMS , GENERAL → EMAIL+APP
        IF V_PRIORITY = 'EMERGENCY' THEN
            V_CHANNELS.EXTEND(3); V_CHANNELS(1) := 'EMAIL'; V_CHANNELS(2) := 'APP'; V_CHANNELS(3) := 'SMS';
        ELSE
            V_CHANNELS.EXTEND(2); V_CHANNELS(1) := 'EMAIL'; V_CHANNELS(2) := 'APP';
        END IF;
        FOR ch IN 1 .. V_CHANNELS.COUNT LOOP
            INSERT INTO DISTRIBUTIONS (DIST_ID, DOC_ID, CHANNEL, RECIPIENT_GROUP, SENT_DATE, STATUS)
            VALUES (SEQ_DIST.NEXTVAL, P_DOC_ID, V_CHANNELS(ch),
                    'กลุ่มเป้าหมายตามสิทธิ์ (' || V_DOCTYPE || ')', SYSDATE, 'SENT');
        END LOOP;
        UPDATE DOCUMENTS SET STATUS = 'DISTRIBUTED' WHERE DOC_ID = P_DOC_ID;

        -- แจ้งเตือนรายบุคคลทุกคนในกลุ่มเป้าหมาย (พนักงาน ROLE_ID = 4)
        FOR r IN (SELECT EMP_ID FROM EMPLOYEES WHERE ROLE_ID = 4) LOOP
            INSERT INTO NOTIFICATIONS (NOTIF_ID, DOC_ID, EMP_ID, CHANNEL, NOTIF_TYPE, SENT_AT)
            VALUES (SEQ_NOTIF.NEXTVAL, P_DOC_ID, r.EMP_ID, 'EMAIL', 'NEW', SYSDATE);
        END LOOP;
    END IF;
    COMMIT;
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;   -- ถ้ากระจายไม่ครบ/ผิดพลาด ย้อนทั้ง Transaction กันข้อมูลครึ่ง ๆ กลาง ๆ
        RAISE;
END;
/

อ่านเป็นช่วง ๆ (ท่องจุดนี้ได้ = ตอบอาจารย์ได้เกือบทุกคำถามเรื่อง Transaction):

  1. ตรวจสิทธิ์ผู้พิจารณา — COUNT คนที่ EMP_ID ตรง และ ROLE_ID = 3 (APPROVER) ถ้าไม่ใช่ raise -20003 (error demo ที่ 2)
  2. ล็อกเอกสาร FOR UPDATE + ดึงประเภท/ความเร่งด่วนไว้ตัดสินใจช่วงหลัง
  3. INSERT APPROVALS — เก็บผลพิจารณา + เหตุผลตีกลับ (UC07)
  4. XOR Gateway: REJECTED → สถานะ REJECTED (จบ ยันธุรการแก้แล้วส่งใหม่ผ่าน SP_SUBMIT_DOC ตาม DR-Ann-101) · APPROVED → เดินต่อช่วง 5
  5. ลงนามอิเล็กทรอนิกส์ — INSERT SIGNATURES (hash จากรหัสเอกสาร+เวลา) ยืนยันกฎ BR-Ann-102: มีลายเซ็นก่อน จึงเผยแพร่ได้ — สถานะ APPROVED → SIGNED
  6. AND Gateway ขา 1 — จัดเก็บ + Doc ID เป็นรหัสอ้างอิง (สถานะ SIGNED คงอยู่)
  7. AND Gateway ขา 2 — กระจายตามความเร่งด่วน: V_CHANNELS คือ array (ODCIVARCHAR2LIST) — EMERGENCY = EMAIL+APP+SMS (3), GENERAL = EMAIL+APP (2) → วน INSERT DISTRIBUTIONS → สถานะ DISTRIBUTED
  8. แจ้งเตือนรายบุคคล — วนพนักงานทุกคน (ROLE_ID = 4) INSERT NOTIFICATIONS type NEW — เริ่มชีวิต UC01/UC02
  9. COMMIT เดียวจบ — ทั้ง 6 ขั้นข้างบนคือ Transaction เดียว · โดน error อะไรก็แล้วแต่ WHEN OTHERS → ROLLBACK ทิ้งทั้งหมด (Atomicity)

ทดสอบจริง — เดิน Flow ครบ 1 รอบ

-- 1) CEO (1002) อนุมัติเอกสาร 5001
EXEC SP_DECIDE_APPROVAL(5001, 1002, 'APPROVED', null);
-- ผล: สถานะ 5001 = DISTRIBUTED · APPROVALS 1 แถว · SIGNATURES 1 แถว
--     DISTRIBUTIONS 2 แถว (GENERAL: EMAIL+APP) · NOTIFICATIONS 4 แถว (กลุ่มเป้าหมาย 1004–1007)

-- 2) ทดสอบตีกลับ (XOR อีกทาง) เอกสาร 5003 ให้ Manager (1003) ตีกลับพร้อมเหตุผล
EXEC SP_DECIDE_APPROVAL(5003, 1003, 'REJECTED', 'เนื้อหาไม่ครบ กรุณาเพิ่มรายละเอียดวันอนุญาต');
-- ผล: สถานะ 5003 = REJECTED · APPROVALS เก็บเหตุผล — ธุรการแก้แล้วส่งใหม่ได้:
EXEC SP_SUBMIT_DOC(5003);   -- REJECTED → PENDING (วนกลับเข้ากระบวนการตาม Flow)

ก้อนที่ 4 · SP_ACKNOWLEDGE_DOC — ยืนยันรับทราบ + ตรวจครบ 100%

03_PLSQL.sql · PROCEDURE 3 
-- ---------- PROCEDURE 3 : พนักงานเปิดอ่าน + กดยืนยันรับทราบ ----------
CREATE OR REPLACE PROCEDURE SP_ACKNOWLEDGE_DOC (
    P_DOC_ID IN NUMBER,
    P_EMP_ID IN NUMBER,
    P_IP     IN VARCHAR2
) IS
    V_TARGET NUMBER;
    V_DONE   NUMBER;
BEGIN
    INSERT INTO READ_LOGS (LOG_ID, DOC_ID, EMP_ID, READ_AT, IP_ADDRESS)
    VALUES (SEQ_LOG.NEXTVAL, P_DOC_ID, P_EMP_ID, SYSDATE, P_IP);

    -- ตรวจสอบสถานะรับทราบว่าครบ 100% หรือยัง (ตาม SLA Metadata ของเอกสาร)
    SELECT COUNT(*) INTO V_TARGET FROM EMPLOYEES WHERE ROLE_ID = 4;
    SELECT COUNT(*) INTO V_DONE FROM READ_LOGS WHERE DOC_ID = P_DOC_ID;

    IF V_DONE >= V_TARGET THEN
        UPDATE DOCUMENTS SET STATUS = 'COMPLETED' WHERE DOC_ID = P_DOC_ID;
    END IF;
    COMMIT;
EXCEPTION
    WHEN DUP_VAL_ON_INDEX THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20010, 'พนักงานนี้ยืนยันรับทราบเอกสารนี้ไปแล้ว ห้ามยืนยันซ้ำ (BR-Memo-103)');
    WHEN OTHERS THEN
        ROLLBACK;
        RAISE;
END;
/
  • INSERT ลง READ_LOGS (เก็บ IP เป็นหลักฐาน) — ถ้ายืนยันซ้ำ UNIQUE (DOC_ID, EMP_ID) จะโยน DUP_VAL_ON_INDEX ที่เราจับไว้ → raise -20010 (error demo ที่ 3) — กันยืนยันซ้ำ 2 ชั้น: DB กันด้วย UNIQUE + โค้ดแปลงเป็นข้อความไทยให้อ่านง่าย
  • เทียบ จำนวนคนยืนยันแล้ว (READ_LOGS) กับ กลุ่มเป้าหมายทั้งหมด (พนักงาน ROLE_ID = 4) — ครบแล้วย้ายสถานะเป็น COMPLETED ตาม XOR Gateway 2 ขา "Ack_Status = COMPLETED_100%"

ทดสอบจริง

EXEC SP_ACKNOWLEDGE_DOC(5001, 1004, '10.0.0.5');   -- ปกรณ์ (1004) ยืนยัน → 1/4
EXEC SP_ACKNOWLEDGE_DOC(5001, 1004, '10.0.0.5');   -- ยืนยันซ้ำ! → ORA-20010 (โชว์ error นี้)
-- ให้ยืนยันครบอีก 3 คน: 1005 กมลวรรณ, 1006 ธนกร, 1007 พิมพ์ชนก
-- → การยืนยันครั้งที่ 4 (แถวสุดท้าย) จะย้ายสถานะเอกสารเป็น COMPLETED อัตโนมัติ
SELECT STATUS FROM DOCUMENTS WHERE DOC_ID = 5001;  -- หลังครบ 4/4 = COMPLETED

ก้อนที่ 5 · SP_CHECK_SLA_REMIND — เกิน 24 ชม. ยังไม่ครบ → เตือนซ้ำ

03_PLSQL.sql · PROCEDURE 4 
-- ---------- PROCEDURE 4 : ตรวจ SLA — เกิน 24 ชม. ยังไม่ครบ → ส่งการแจ้งเตือนซ้ำ ----------
CREATE OR REPLACE PROCEDURE SP_CHECK_SLA_REMIND (P_DOC_ID IN NUMBER) IS
    V_FIRST_SENT DATE;
    V_UNREAD     NUMBER;
BEGIN
    SELECT MIN(SENT_DATE) INTO V_FIRST_SENT FROM DISTRIBUTIONS WHERE DOC_ID = P_DOC_ID;

    SELECT COUNT(*) INTO V_UNREAD
    FROM EMPLOYEES e
    WHERE e.ROLE_ID = 4
      AND NOT EXISTS (SELECT 1 FROM READ_LOGS r
                      WHERE r.DOC_ID = P_DOC_ID AND r.EMP_ID = e.EMP_ID);

    IF V_UNREAD > 0 AND (SYSDATE - V_FIRST_SENT) * 24 >= 24 THEN
        FOR r IN (SELECT e.EMP_ID FROM EMPLOYEES e
                  WHERE e.ROLE_ID = 4
                    AND NOT EXISTS (SELECT 1 FROM READ_LOGS r
                                    WHERE r.DOC_ID = P_DOC_ID AND r.EMP_ID = e.EMP_ID)) LOOP
            INSERT INTO NOTIFICATIONS (NOTIF_ID, DOC_ID, EMP_ID, CHANNEL, NOTIF_TYPE, SENT_AT)
            VALUES (SEQ_NOTIF.NEXTVAL, P_DOC_ID, r.EMP_ID, 'APP', 'REMINDER', SYSDATE);
        END LOOP;
        COMMIT;
    END IF;
END;
/
  • MIN(SENT_DATE) จาก DISTRIBUTIONS = เวลาที่กระจายครั้งแรก → จุดเริ่มนับ SLA
  • NOT EXISTS = หา "คนที่ยังไม่มีแถวยืนยัน" — เทคนิคเดียวกับ LEFT JOIN ... IS NULL (เจออีกแบบในหน้า JOIN)
  • (SYSDATE - V_FIRST_SENT) * 24 >= 24 — ใน Oracle วันลบวัน = จำนวนวัน (มีทศนิยม) คูณ 24 = ชั่วโมง — เงื่อนไขตามกฎ BR-Memo-101/DR-Memo-102
  • ผ่านเงื่อนไข → วน INSERT NOTIFICATIONS type REMINDER ให้เฉพาะคนที่ยังไม่อ่าน (ไม่รบกวนคนที่อ่านแล้ว — กฎ BR-Memo-102 ส่งเฉพาะกลุ่มเป้าหมาย) แล้ว COMMIT · ถ้ายังไม่เกิน 24 ชม. Procedure จบเงียบ ๆ ไม่ทำอะไร

❓ Q&A ของหน้านี้ (อาจารย์ชอบถามตอนรัน PL/SQL)

คำถามคำตอบสั้น
Transaction อยู่ตรงไหนของระบบนี้SP_DECIDE_APPROVAL — บันทึกผล + ลงนาม + กระจาย + แจ้งเตือน ใน Transaction เดียว จบด้วย COMMIT 1 ครั้ง ผิดพลาด ROLLBACK ทั้งหมด (Atomicity)
ทำไมต้อง FOR UPDATEล็อกแถวเอกสารระหว่างอ่านสถานะจนตัดสินใจ — กันสองคนแก้พร้อมกัน (Concurrency Control)
Trigger ทำอะไร ต่างจาก ProcedureTrigger = ฐานข้อมูลยิงเองเมื่อเหตุการณ์เกิด (หลัง UPDATE STATUS) · Procedure = เราเรียกใช้ด้วย EXEC
ถ้ากระจายขาดกลางคันเกิดอะไรขึ้นEXCEPTION WHEN OTHERS → ROLLBACK — ลงนาม/บันทึกผลที่ทำไปแล้วถูกย้อนหมด ข้อมูลไม่ครึ่ง ๆ กลาง ๆ
SLA 24 ชม. ทำงานยังไงSP_CHECK_SLA_REMIND: (SYSDATE − เวลากระจายครั้งแรก) × 24 ≥ 24 และยังมีคนไม่ยืนยัน → INSERT NOTIFICATIONS type REMINDER เฉพาะคนที่ยังไม่อ่าน
ป้องกันยืนยันซ้ำยังไง2 ชั้น — UNIQUE (DOC_ID, EMP_ID) ใน READ_LOGS + EXCEPTION DUP_VAL_ON_INDEX แปลงเป็น ORA-20010
Sequence ใช้ตรงไหนออกรหัสอัตโนมัติทุกตารางทรานแซกชัน: SEQ_APPROVAL/SEQ_SIGN/SEQ_DIST/SEQ_NOTIF/SEQ_LOG — ตรง To-Be "จัดเก็บ + ออกรหัสอ้างอิง"

Q ระหว่าง SP_DECIDE_APPROVAL ทำงานอยู่ ถ้า INSERT DISTRIBUTIONS ล้มเหลว (เช่น ตารางพัง) ผลลัพธ์คืออะไร?

เฉลย: WHEN OTHERS → ROLLBACK + RAISE — คุณสมบัติ Atomicity: Transaction ต้องสำเร็จทั้งชุด ไม่มี COMMIT ครึ่ง ๆ
