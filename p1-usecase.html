📨 ระบบนี้ทำอะไร (เล่าเปิด demo 30 วินาที)

ระบบแจ้งข้อความเวียนและประกาศภายในองค์กร — เดิมทำงานด้วยเอกสารกระดาษ: ฝ่าย HR กำหนดผู้รับ → เจ้าหน้าที่ธุรการร่างประกาศ/จดหมายเวียน → เลขาเดินเอกสารส่ง CEO/Manager พิจารณาลงนาม → เดินกลับไปกระจายให้พนักงานเปิดอ่าน เซ็นรับทราบ ส่งต่อกันจนครบ — ช้า ตามไม่ทัน และไม่มีหลักฐานว่าใครยังไม่รับทราบ

ระบบใหม่ (To-Be) ทำบนฐานข้อมูล: ร่างด้วยแม่แบบ + ตั้ง SLA → อนุมัติ/ตีกลับบนระบบ (XOR Gateway) → ลงนามอิเล็กทรอนิกส์ (กฎ BR-Ann-102: ห้ามเผยแพร่ก่อนลงนาม) → กระจายหลายช่องทาง (EMAIL/APP/SMS ตามความเร่งด่วน) → พนักงานยืนยันรับทราบ + เก็บ Timestamp เป็นหลักฐาน → ครบ 100% จบ, ยังไม่ครบและเกิน 24 ชม. (SLA) → ระบบเตือนซ้ำอัตโนมัติ

ทุกฟังก์ชัน «include» UC09 เข้าสู่ระบบ — ยืนยันตัวตนก่อนใช้งานทุกกรณี

«include» อ่านว่า "อินคลูด" — Base UC เรียกใช้ Subroutine ทุกครั้งที่รัน ไม่มีเงื่อนไข — UC01–08 ทุกตัวต้องผ่าน UC09 (ยืนยันตัวตน) ก่อนเสมอ จึงลากเส้น «include» ไปหา UC09 หมด

ต่างจาก «extend» (ถ้าโดนถาม) — «extend» = เส้นที่ "เกิดเฉพาะบางเงื่อนไข" (เช่น ตอนพิมพ์เอกสารถึงจะเรียกฟังก์ชันแปลงเป็น PDF) · จำง่าย ๆ: «include» = ทุกครั้ง (จำเป็น) · «extend» = บางครั้ง (เสริม) — ใน diagram ของ Part I มีแต่ «include»

🎤 เล่า UC Diagram เปิด demo ด้วย 4 ประโยค (ท่องได้ = เริ่มอย่างมั่นใจ)

  1. "ระบบนี้มี 4 Actor: พนักงานกลุ่มเป้าหมาย (รับ-อ่าน-ยืนยัน), ธุรการ (ร่าง-แก้), ผู้บริหาร (อนุมัติ-ตีกลับ), และ IT (จัดการสิทธิ์)"
  2. "มี 9 Use Case ครอบตั้งแต่ร่างเอกสารจนถึงยืนยันรับทราบ โดยทุก UC «include» UC09 เข้าสู่ระบบ"
  3. "Flow หลักคือ: ร่าง → ส่งอนุมัติ → อนุมัติ/ตีกลับ (XOR) → ลงนาม → กระจาย → ยืนยันครบ 100% หรือเตือนซ้ำเกิน SLA"
  4. "ทุก UC นี้แปลงเป็นตาราง 11 ตารางและ PL/SQL 4 ตัวหน้าถัดไป — เช่น UC02 ยืนยันรับทราบ คือตาราง READ_LOGS + SP_ACKNOWLEDGE_DOC"

UC-01 · รับการแจ้งเตือนและเปิดอ่านเอกสาร

Related RequirementsUS8
Initiating Actorพนักงานกลุ่มเป้าหมาย
Actor's Goalให้พนักงานได้รับการแจ้งเตือนเมื่อมีประกาศใหม่ผ่านระบบแจ้งเตือนอีเมล เพื่ออ่านจดหมายเวียนหรือประกาศ
Participating Actorsระบบสารสนเทศ
Preconditions1. พนักงานต้องมีอีเมลอยู่ในระบบ · 2. มีการสร้างและอนุมัติส่งประกาศ/จดหมายเวียนใหม่ในระบบ
Postconditions1. ระบบบันทึก Log การส่ง Email แจ้งเตือนสำเร็จ · 2. พนักงานเข้าไปอ่านประกาศหรือจดหมายเวียน
Flow (Main Success)← 1. เมื่อมีการส่งประกาศหรือจดหมายเวียน
← 2. พนักงานได้รับแจ้งเตือนผ่าน Email
→ 3. พนักงานเข้าไปอ่านประกาศหรือจดหมายเวียน

🗄️ เก็บใน DB: NOTIFICATIONS (แจ้งเตือน NEW) — สร้างโดย SP_DECIDE_APPROVAL ตอนกระจายเอกสาร

UC-02 · อ่านและกดยืนยันรับทราบเอกสาร

Related RequirementsUS9
Initiating Actorพนักงานกลุ่มเป้าหมาย
Actor's Goalยืนยันการรับทราบประกาศหรือข้อความเวียน
Preconditions1. เข้าสู่ระบบ · 2. เปิดอ่านประกาศ/ข้อความเวียน · 3. ยืนยันรับทราบ
Postconditionsบันทึก User ID, Document ID, Timestamp (หลักฐานรับทราบ)
Flow (Main Success)← 1. ระบบแสดงเนื้อหาเอกสารและปุ่มรับทราบ
→ 2. พนักงานอ่านเนื้อหาเลื่อนลงจนถึงด้านล่างสุด
→ 3. พนักงานกดปุ่มรับทราบ
← 4. ระบบบันทึกข้อมูล User ID, Document ID, Timestamp
Extensions1a. พนักงานไม่เปิดอ่านเอกสาร → ระบบส่งแจ้งเตือนซ้ำ
3a. กดรับทราบก่อนเลื่อนอ่านจนสุด → ระบบล็อกปุ่มรับทราบจนกว่าจะเลื่อนดูจนสุด

🗄️ เก็บใน DB: READ_LOGS + SP_ACKNOWLEDGE_DOC — UNIQUE (DOC_ID, EMP_ID) กันยืนยันซ้ำ + ครบ 100% แล้วเลื่อนสถานะเป็น COMPLETED

UC-03 · ดูประกาศย้อนหลังและดูสถานะเอกสาร

Related RequirementsUS10
Initiating Actorพนักงานกลุ่มเป้าหมาย
Actor's Goalตรวจสอบเนื้อหาและสถานะย้อนหลังได้
Preconditions1. มีข้อมูลประกาศในระบบ · 2. เข้าสู่ระบบ
Postconditionsแสดงสถานะและข้อความประกาศ
Flow (Main Success)→ 1. เมื่อต้องการตรวจสอบสถานะ
→ 2. ค้นหาประกาศ/ข้อความเวียนที่ต้องการในระบบ
← 3. ระบบแสดงสถานะและข้อความประกาศ
Extensions2a. ไม่เจอประกาศ/ข้อความเวียนที่ต้องการ → ระบบแจ้งเตือนว่าไม่มีเอกสารที่ตามหา

🗄️ เก็บใน DB: DOCUMENTS (สถานะปัจจุบัน) + DOC_STATUS_LOG (Audit Trail จาก Trigger — สถานะย้อนหลังทุกจุดเปลี่ยน)

UC-04 · ร่างเอกสารด้วยแม่แบบและตั้งค่า SLA

Related RequirementsUS3, US4
Initiating Actorเจ้าหน้าที่ธุรการส่วนกลาง
Actor's Goalสร้างร่างประกาศหรือข้อความเวียนตามแม่แบบ และกำหนดกรอบเวลาการอ่าน
Preconditionsมีแม่แบบเอกสารพร้อมใช้งาน
Postconditionsได้ประกาศ/ข้อความเวียนตามแม่แบบ และมีการกำหนดกรอบเวลาการอ่าน
Flow (Main Success)→ 1. เจ้าหน้าที่เลือกหมวดหมู่แม่แบบที่จะใช้
← 2. ระบบแสดงแบบฟอร์มเอกสารตามแม่แบบที่เลือก
→ 3. กรอกเนื้อหา เลือกกลุ่มเป้าหมาย และกำหนดกรอบเวลาการอ่าน
→ 4. เจ้าหน้าที่บันทึกเอกสาร
← 5. ระบบบันทึกข้อมูลร่างเอกสาร
Extensions1a. ไม่มีแม่แบบที่ต้องการ → ต้องทำแบบขึ้นมาเอง
3a. ลืมเลือกกลุ่มเป้าหมาย/กรอบเวลาอ่าน → ระบบแจ้งเตือนให้กรอก มิฉะนั้นบันทึกไม่ได้

🗄️ เก็บใน DB: DOCUMENTS (สถานะ DRAFT + คอลัมน์ SLA_HOURS DEFAULT 24 + SEQ_DOC ออกรหัสเอกสาร)

UC-05 · ดึงเนื้อหาจากประกาศมาสร้างข้อความเวียน

Related RequirementsUS4
Initiating Actorเจ้าหน้าที่ธุรการส่วนกลาง
Actor's Goalสร้างข้อความเวียนที่มีเนื้อหาเดียวกับประกาศได้รวดเร็ว ไม่ต้องพิมพ์ซ้ำซ้อน
Preconditions1. เข้าสู่ระบบด้วยสิทธิ์ Document Creator · 2. มีประกาศหลักที่ผ่านการอนุมัติ และต้องการทำจดหมายเวียน
Postconditions1. ได้ร่างข้อความเวียนฉบับใหม่ที่ Copy เนื้อหาจากประกาศหลัก พร้อมปรับแต่งและส่งขออนุมัติต่อ · 2. ระบบ Save อัตโนมัติและรอธุรการกดส่ง
Flow (Main Success)→ 1. หาประกาศที่ต้องการแปลงเป็นข้อความเวียน
→ 2. กดสร้างประกาศเป็นข้อความเวียน
← 3. ระบบ Copy ข้อมูลสำคัญอัตโนมัติ
→ 4. ตรวจเช็คและเติมส่วนสำคัญที่ระบบไม่ได้เติมให้
→ 5. กดส่งเอกสาร
← 6. ระบบส่งไปให้ CEO อนุมัติเอกสาร
Extensions5a. ไม่ได้กดส่ง → ระบบ Save อัตโนมัติและรอธุรการมากดส่ง

🗄️ เก็บใน DB: DOCUMENTS (คอลัมน์ DOC_TYPE แยก ANNOUNCEMENT / MEMO — ประกาศและข้อความเวียนเป็นตารางเดียวกัน ต่างประเภท)

UC-06 · แก้ไขและส่งร่างเอกสารใหม่กรณีถูกตีกลับ

Related RequirementsUS5
Initiating Actorเจ้าหน้าที่ธุรการส่วนกลาง
Actor's Goalแก้ร่างที่ถูกตีกลับ แล้วส่งขออนุมัติใหม่ให้ผู้อนุมัติคนเดิม
Preconditions1. เจ้าหน้าที่ธุรการเข้าสู่ระบบ · 2. มีเอกสารที่ถูกตีกลับ
Postconditionsได้เอกสารฉบับที่แก้ไข พร้อมส่งต่อไปยังผู้อนุมัติคนเดิม
Flow (Main Success)← 1. ระบบแจ้งเตือนมีเอกสารถูกตีกลับ
→ 2. เข้ามาดูเอกสารที่ถูกตีกลับ
← 3. ระบบแสดงเนื้อหาเดิม พร้อมเหตุผลที่ถูกตีกลับจากผู้อนุมัติ
→ 4. กดแก้ไขเอกสาร
← 5. ระบบเปิดให้แก้เนื้อหาและอัปโหลดไฟล์แนบใหม่
→ 6. แก้ไขเนื้อหา/เลือกกลุ่มเป้าหมายใหม่
→ 7. ส่งขออนุมัติซ้ำ
← 8. ระบบบันทึกเอกสารใหม่
← 9. ระบบส่งการแจ้งเตือนไปยังผู้อนุมัติ
Extensions3a. พิจารณาแล้วเห็นควรยกเลิกเผยแพร่ → กดยกเลิกเอกสาร → ระบบปิดการเข้าถึงเอกสาร

🗄️ เก็บใน DB: APPROVALS (คอลัมน์ REASON = เหตุผลตีกลับ) + สถานะ REJECTED บน DOCUMENTS — แก้แล้วส่งใหม่ผ่าน SP_SUBMIT_DOC (ยอมรับ DRAFT/REJECTED เท่านั้น)
