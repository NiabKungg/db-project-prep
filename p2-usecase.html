หน้าแรก • PART II — S2G13 Public Transit Navigation System (อ.ผึ้ง)

🚌 Use Case 10 ตัว + Traceability REG1–17 — ระบบช่วยเดินทางโดยรถขนส่งสาธารณะ

4 Actor10 Use CaseREQ 17 ข้อREG1–17 ↔ UC

🔗 เอกสาร UC/REQ นี้สัมพันธ์กับอะไรที่จะสาธิตจริง

Use Case และ REQ 17 ข้อในหน้านี้คือ เอกสาร Business Domain ของงาน อ.ผึ้ง (Public Transit Navigation) ที่ Traceability อ้างอิง — ส่วน ระบบที่ implement จริงและ deploy บน server แล้วสำหรับสาธิต คือ Smart Bus Bell & IoT Tracking System (11 ตาราง + Procedure 4 ตัว) ซึ่งรองรับกลุ่ม UC ใจกลางเรื่อง "กดกริ่ง–แจ้งเตือน–ติดตามรถ" (UC04/UC05/UC01/UC10) — หน้าถัดไปจะสอนโค้ดจริงทีละบล็อก และท้ายหน้านี้มีตารางจับคู่ UC ↔ ตารางใหม่ให้ตอบอาจารย์ได้ว่า "UC นี้ implement ด้วยอะไร"

① อาจารย์ต้องการอะไร (โจทย์ Part II เหมือน Part I ทุกข้อ)

"DDL , DML ตาม E/R Diagram" + "PL/SQL ตามโจทย์หลักของระบบงาน" + "JOIN แสดงข้อมูลการทำงานหลัก" — Business Domain เปลี่ยนเป็น ระบบช่วยเดินทางโดยรถขนส่งสาธารณะ (Public Transit Navigation) — ทุกคนต้องเล่าได้ว่าระบบนี้แก้ปัญหาอะไร ใครใช้ และทำไมตาราง/Procedure ทุกตัวถึงมีอยู่ (มาจาก UC ตัวไหน)

🚌 ระบบนี้แก้ปัญหาอะไร (เล่าเปิด demo 30 วินาที — จากเอกสารความต้องการจริง)

ปัญหาเดิม: ผู้ใช้รถเมล์/สองแถว ไม่รู้ว่ารถคันถัดไปอยู่ไหน ต้องรอนานเท่าไร · ช่วงโมงเร่งด่วนรถแน่นจนขึ้นไม่ได้แต่เช็คไม่ได้ล่วงหน้า · รถสองแถวยืนท้ายรถแล้วต้องเอื้อมมือกดกริ่งลงรถ เสี่ยงอุบัติเหตุ · ฝั่งคนขับมองไม่เห็นคนรอตามจุดจอดมืดหรือไม่ชัดเจน

ระบบใหม่: ผู้โดยสาร ดูตำแหน่งรถบนแผนที่แบบ real-time + เช็คความหนาแน่น (ว่าง/ปานกลาง/แน่น) + กดกริ่งลงรถผ่านแอป + รับแจ้งเตือนรถใกล้ถึง — คนขับมีหน้าจอแจ้งเตือน "มีคนรอขึ้น/ต้องการลง" จุดจอดถัดไป และกดเปลี่ยนสถานะรถให้ข้อมูลตรงความจริง — ฝั่ง Admin จัดการสายรถ/จุดจอด/เส้นทาง และดาวน์โหลดประวัติรอบวิ่งมาตรวจสอบย้อนหลัง

«include» — Base UC เรียกใช้ UC10 ทุกครั้งแบบบังคับ (ยืนยันตัวตนก่อน) · participate — Actor ช่วยร่วมทำ (พนักงานบนรถรับสัญญาณกริ่งใน UC04) · Participating Actors (ระบบ) — ระบบย่อยที่ถูกเรียกใช้: ระบบ GPS, ระบบค้นหาอาคาร/ย่านทานะ, ระบบแจ้งเตือนสถานะรถ, Trip History Service, ระบบจัดการข้อมูลผู้ใช้งาน

อ่านสาย Flow: → = Actor ทำ / ← = System ตอบสนอง · Extensions = กรณีผิดปกติ

UC-01 · ดูพิกัดตำแหน่งรถบนแผนที่

Related RequirementsREQ-01, REQ-14
Initiating Actorผู้โดยสาร
Actor's Goalตรวจสอบตำแหน่งปัจจุบันของรถเมล์/สองแถวบนแผนที่
Participating Actorsระบบ GPS
Preconditions1. ผู้ใช้งานเปิดแอปและเชื่อมต่ออินเทอร์เน็ต · 2. รถโดยสารเปิดใช้งาน GPS อยู่
Postconditionsระบบแสดงตำแหน่งรถโดยสารที่เคลื่อนที่อยู่ในขณะนั้น
Flow (Main Success)→ 1. ผู้โดยสารเลือกดูแผนที่ตำแหน่งรถ
← 2. ระบบดึงพิกัด GPS ของรถที่กำลังใช้งาน
← 3. ระบบแสดงตำแหน่งรถบนแผนที่
Extensions2a. ไม่มีรถให้บริการในสายที่เลือก ณ เวลานั้น → "ขณะนี้ยังไม่มีรถเปิดให้บริการในเส้นทางนี้"
2b. สัญญาณ GPS ขาดหาย/ไม่เสถียร → "ไม่พบข้อมูลรถโดยสารในขณะนี้"

🗄️ เก็บใน DB (ฉบับ implement): IOT_BOX (กล่อง IoT — พิกัด LAT/LONG + LAST_PING_AT = ตำแหน่งล่าสุดของรถ)

UC-02 · ดูสายรถ เส้นทาง และอัตราค่าโดยสาร

Related RequirementsREQ-04, REQ-03
Initiating Actorผู้โดยสาร
Actor's Goalดูข้อมูลสายรถ เส้นทางที่วิ่งผ่าน จุดจอด และอัตราค่าโดยสาร
Participating Actorsระบบฐานข้อมูลเส้นทาง (ค้นหาอาคาร/ย่านใกล้เคียง — LANDMARK)
Preconditions1. มีข้อมูลสายรถ เส้นทาง จุดจอดอยู่ในระบบ · 2. โทรศัพท์เชื่อมต่ออินเทอร์เน็ต
Postconditionsระบบแสดงข้อมูลเส้นทาง จุดจอด และราคาค่าโดยสาร
Flow (Main Success)→ 1. ผู้โดยสารค้นหาสายรถหรือจุดจอดที่ต้องการ
← 2. ระบบแสดงสายรถ เส้นทางที่วิ่ง จุดจอด ค่าโดยสาร
← 3. ระบบคำนวณและแสดงเวลาที่มาถึงจุดจอดที่ใกล้ที่สุด
Extensions2a. ค้นหาจุดจอดหรือสายรถไม่พบ → "ไม่พบข้อมูลที่ค้นหา"

🗄️ เก็บใน DB (ฉบับ implement): VEHICLE เก็บทะเบียน + ROUTE_NO (สายเดินรถ) — ค้นสายได้จากทะเบียน (จุดจอดรายละเอียดไม่อยู่ในขอบเขตฉบับสาธิต)

UC-03 · ตรวจสอบสถานะความหนาแน่นบนรถ

Related RequirementsREQ-05
Initiating Actorผู้โดยสาร
Actor's Goalเช็คระดับความแน่นของรถก่อนตัดสินใจขึ้น
Participating Actorsระบบติดตามสถานะยานพาหนะ
Preconditionsพนักงานอัปเดตสถานะความหนาแน่นของคนบนรถแล้ว
Postconditionsระบบแสดงความหนาแน่นของคนบนรถ
Flow (Main Success)→ 1. ผู้โดยสารเลือกรถที่ต้องการดูความหนาแน่น
← 2. ระบบดึงข้อมูลระดับความหนาแน่น
← 3. ระบบแสดงป้ายสถานะ 3 ระดับ: "ว่าง" / "ปานกลาง" / "แน่น" พร้อมไอคอนสีประกอบ
Extensions2a. ข้อมูลไม่มีการอัปเดตนาน → เตือน "รถคันนี้สถานะอาจไม่เป็นปัจจุบัน"

🗄️ เก็บใน DB: ไม่มีคอลัมน์! "จำนวนคนบนรถ" เป็น Derived Attribute ตาม ER (วงรีเส้นประ) — ไม่เก็บ คำนวณจากตัวนับ IoT/แอปคนขับ (คำตอบโจทย์ ER ข้อนี้)

UC-04 · กดกริ่งลงรถผ่านแอปพลิเคชัน

Related RequirementsREQ-06, REQ-09, REQ-17
Initiating Actorผู้โดยสาร
Actor's Goalแจ้งพนักงานขับรถว่าต้องการลงจุดจอดถัดไป โดยไม่ต้องเอื้อมมือกดกริ่งบนรถ
Participating Actorsพนักงานขับรถ, ระบบติดตามยานพาหนะ (พนักงานบนรถ participate)
Preconditions1. ผู้โดยสารเข้าสู่ระบบ («include» UC10) · 2. ผู้โดยสารอยู่บนรถ
Postconditions1. ระบบส่งสัญญาณกริ่งสำเร็จ · 2. พนักงานขับรถได้รับสัญญาณกริ่ง
Flow (Main Success)→ 1. ผู้โดยสารกด "กดกริ่งลงรถ" บนแอปพลิเคชัน
← 2. ระบบส่งสัญญาณไปให้พนักงานขับรถ
← 3. ระบบแสดงข้อความยืนยันแก่ผู้โดยสารว่า "กดกริ่งสำเร็จ"
Extensions1a. ยังไม่ได้เข้าสู่ระบบ → ระบบแจ้งให้เข้าสู่ระบบก่อนใช้ฟังก์ชันนี้ (UC10)
2a. เครือข่ายขัดข้อง ส่งสัญญาณไม่สำเร็จ → "ส่งสัญญาณไม่สำเร็จ กรุณากดใหม่อีกครั้ง หรือกดกริ่งบนตัวรถโดยตรง"

🗄️ เก็บใน DB (ฉบับ implement ⭐): BELL_REQUEST (สถานะ SENDING/SUCCESS/CANCELLED + ALIGHT_TIME) + junction VEHICLE_BELL_REQUEST + SP_PRESS_BELL — 1 transaction = 3 DML: กริ่ง → ส่งถึงรถ → สถิติ + ตรวจบทบาท PASSENGER ก่อน (-20001)

UC-05 · รับการแจ้งเตือนเมื่อรถใกล้ถึงจุดจอด

Related RequirementsREQ-07, REQ-08
Initiating Actorผู้โดยสาร
Actor's Goalรับแจ้งเตือนเมื่อรถคันที่กำลังรอใกล้ถึงจุดจอด เพื่อเตรียมตัวขึ้นทัน
Participating Actorsระบบแจ้งเตือน, ระบบติดตามพิกัด GPS
Preconditions1. ผู้โดยสารเลือกสายรถที่กำลังรอ («include» UC10) · 2. ผู้โดยสารอนุญาตการแจ้งเตือน
Postconditionsผู้โดยสารได้รับข้อความแจ้งเตือนเมื่อรถเข้าใกล้จุดจอดที่กำหนด
Flow (Main Success)→ 1. ผู้โดยสารเลือกจุดจอดที่รอ
← 2. เมื่อรถเข้าใกล้ ระบบส่งแจ้งเตือนให้ผู้โดยสาร
← 3. ระบบส่งแจ้งเตือนให้คนขับว่ามีคนในจุดจอดถัดไป
Extensions2a. ปิดการรับแจ้งเตือน หรือไม่มีสัญญาณเน็ต → ระบบบันทึกประวัติข้อความเตือนไว้ในกล่องข้อความภายในแอป

🗄️ เก็บใน DB (ฉบับ implement): DIGITAL_BELL_SIGNAL + junction VEHICLE_DIGITAL_SIGNAL + ALERT_STATISTICS (สถิติต่อรถต่อวัน — UNIQUE รถ+วัน) + SP_SEND_DIGITAL_SIGNAL (MERGE +1)

UC-06 · กดเปลี่ยนสถานะของรถ

Related RequirementsREQ-10, REQ-17
Initiating Actorพนักงานขับรถ («include» UC10)
Actor's Goalทำให้สถานะการเดินรถตรงความเป็นจริง (เช่น พร้อมให้บริการ / รถเต็ม / หมดระยะ)
Participating Actorsระบบจัดการสถานะยานพาหนะ, ผู้โดยสาร
Preconditionsพนักงานขับรถเข้าสู่ระบบเรียบร้อยแล้ว
Postconditions1. สถานะรถในฐานข้อมูลส่วนกลางถูกอัปเดต · 2. สถานะใหม่อัปเดตบนหน้าจอผู้โดยสารทันที
Flow (Main Success)→ 1. พนักงานเลือกเมนูเปลี่ยนสถานะรถ
→ 2. กดเลือกสถานะใหม่ที่ต้องการ (เช่น หมดระยะ)
← 3. ระบบบันทึกสถานะใหม่และกระจายข้อมูลอัปเดตไปยังระบบแผนที่ของผู้โดยสาร

🗄️ เก็บใน DB (ฉบับ implement): ฝั่งคนขับคือ SP_COMPLETE_ALIGHT (ยืนยันว่าผู้โดยสารลงแล้ว: SENDING → SUCCESS + ประทับ ALIGHT_TIME — กันยืนยันซ้ำด้วย SQL%ROWCOUNT=0 → -20002)

UC-07 · ดูตำแหน่งรถทุกคันบนแผนที่ภาพรวม

Related RequirementsREQ-02
Initiating Actorผู้ดูแลระบบ
Actor's Goalติดตาม ตรวจสอบ และจัดการการเดินรถทั้งหมดในระบบ
Participating Actorsระบบติดตามยานพาหนะ
Preconditionsผู้ดูแลระบบเข้าสู่ระบบด้วยสิทธิ์ผู้ดูแลระบบ
Postconditionsเห็นตำแหน่ง ทิศทาง และสถานะของรถทุกคันที่กำลังวิ่งบนแผนที่
Flow (Main Success)→ 1. เปิดหน้าจอ "แผนที่ภาพรวมการเดินรถ"
← 2. ระบบดึงข้อมูล GPS ทุกคัน
← 3. ระบบแสดงตำแหน่งรถพร้อมรายละเอียด
Extensions3a. รถบางคันขาดส่งพิกัด GPS นานเกินกำหนด → แสดงไอคอนรถสีเทา/เครื่องหมายเตือนออฟไลน์ (ใช้ตำแหน่งล่าสุดที่มี)
